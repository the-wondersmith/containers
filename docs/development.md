# Local development

A devcontainer based on `mcr.microsoft.com/devcontainers/base:trixie` is provided. Outside it, [mise](tooling.md) is the only prerequisite.

```sh
mise run lint              # shellcheck, shfmt, yamllint, actionlint, editorconfig, melange compile
mise run tests             # definition validation; prints how to run the acceptance suite
mise run build             # every musl component + the .apk (needs docker)
mise run build:deb         # the .deb, by running the real CI jobs under act
mise run versions:refresh  # repoint the melange definitions at current upstream releases
mise run clean             # remove all build output
```

`mise run build` uses the same melange definitions CI does, so a failure locally is a failure there. It works unchanged on macOS because
melange provisions its own Alpine build guest via docker.

## The `.deb` path

`mise run build:deb` deliberately does not reimplement the packaging logic locally. The `.deb` is assembled by
`.github/actions/package/podman/debian` and the glibc podman by `.github/actions/build/podman-gnu`; a second local copy of either would
drift from CI. Instead it drives those same actions with [act](https://github.com/nektos/act), so a pass locally means the CI path works.

The `act:*` task family runs the other workflows the same way — `act:components`, `act:apk`, `act:watch`, `act:prune`,
`act:automerge`, `act:apt-notify`, and `act:doctor` to check the local setup. Event payloads are generated by
`act:fixtures` from the committed melange definitions; everything under `.act/` is gitignored.

## The acceptance suite locally

`mise run tests` validates definitions only. The behavioural suite needs a built package plus privileged container access, so it runs in
CI — `mise run tests` prints the `docker run --privileged --cgroupns=host` invocation for running it by hand against `dist/`.
